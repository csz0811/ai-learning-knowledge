# AI编程全流程模板

> 每次用 AI 编程开发新工具时，按这个流程走。
> 从需求描述 → 交付审查，全链路覆盖。

**核心理念：** AI 是执行者，你 是导演。
→ 需求描述完整 → AI 给出完整代码，而不是只给骨架
→ 你的职责：审查、提问、让 AI 修正

---

## 【第一步】描述清楚你要做什么

| 编号  | 问题            | 你的回答 | 举例                            |
| --- | ------------- | ---- | ----------------------------- |
| 1   | 我要做的是什么系统/工具？ |      | 企业内部知识库问答 API                 |
| 2   | 谁来用？          |      | 内部员工 / 其他系统 API 调用 / AI Agent |
| 3   | 核心功能是什么？      |      | 用户提问 → 检索 PDF → 返回回答          |
| 4   | 数据从哪来？        |      | 上传的 PDF / 数据库 / 网页 / 外部 API   |
| 5   | 数据规模多大？       |      | 小规模先跑通 / 预估 XX 条文档 / 大规模需分布式  |
| 6   | 要支持多少人同时用？    |      | 10人 / 100人 / 不限               |

---

## 【第二步】告诉 AI 你的约束

| 约束项 | 你的选择 |
|--------|---------|
| 部署平台 | 免费平台（Zeabur/Railway/Render）/ 自有服务器 / 云 |
| 技术偏好 | 用 XX 框架 / 沿用现有代码 / 不限制 |
| 预算 | $0 / 有预算（多少） |
| 并发上限 | 预期最大并发数（如100人），是否需要限流保护 |
| 其他限制 | |

---

## 【第三步】告诉 AI 你需要什么

在提问时明确告诉 AI 你需要以下哪些（打 ✅）：

- [ ] 框架选型建议 + 理由
- [ ] 核心代码骨架
- [ ] 异步/并发处理方案
- [ ] 测试场景分析（先问AI"应该测什么"，再生成测试用例）
- [ ] 测试用例（覆盖：正常输入 / 边界值 / 异常输入）
- [ ] 接口文档
- [ ] 部署方式 + 命令
- [ ] Dockerfile / docker-compose 配置
- [ ] 上下文窗口处理（检索结果排序与裁剪策略）
- [ ] 向量数据库抽象层（支持后续切换数据库）

---

## 【第四步】避坑清单（审查项）

> AI 给代码后，逐项审查，发现问题直接追问 AI 修正。

| 审查项 | 问题 | 如果不对怎么问 AI |
|--------|------|------------------|
| **异步处理** | 是否有 `async/await` | "这里需要支持并发，请改成异步写法" |
| **真假异步** | 是否用了异步库（httpx/aiohttp）而非同步库（requests） | "这个 API 调用需要改成异步库，否则等待时会阻塞其他请求" |
| **并发上限保护** | 有没有限流机制（rate limit / Semaphore / 队列） | "并发超限时系统应该排队还是拒绝？请加上保护机制" |
| **数据库抽象** | 是否把具体数据库写死在业务逻辑里 | "请设计一个向量数据库抽象层，支持后续切换数据库" |
| **上下文窗口** | 检索结果是否做了排序和裁剪，优先放最相关内容 | "当检索结果超过上下文限制时，如何排序和裁剪？" |
| **错误处理** | 异常情况有没有捕获（API 超时 / 文件不存在 / 数据库断开） | "如果 XX 失败了，系统会怎样？请补上异常处理" |
| **测试覆盖** | 核心功能有没有测试用例覆盖 | "请补上 XX 的测试用例，覆盖正常/异常/边界三种情况" |

---

## 【第五步】交付检查清单

每次 AI 给完代码，对照这个检查：

```
□ 代码本地能跑通
□ 测试用例全部通过
□ 接口文档 /docs 可访问
□ 部署命令已在目标平台验证
□ 核心功能的边界情况有覆盖
□ 没有硬编码的敏感信息（API Key 放 .env）
□ README 有运行说明
```

## 附录 A：测试场景发现模板

> 每个项目开始前，用这个问 AI，找出"应该测什么"

```
【问AI】"我准备做 [系统描述]，请帮我分析：

1. 这个系统的输入边界在哪？（什么算正常/异常/边界输入）
2. 这个系统依赖哪些外部服务？（LLM API / 数据库 / 文件系统）
3. 这个系统的核心功能是什么？（最重要的1-2个，不能出错的是什么）

基于以上分析，我应该重点测试哪些场景？"
```

AI 回答后整理成表：

| 系统模块 | 正常场景 | 异常场景 | 边界场景 |
|---------|---------|---------|---------|
| 检索模块 | | | |
| 生成模块 | | | |
| API接口 | | | |

## 附录 B：向量数据库选型指南

> 根据数据规模和场景选择，不是越大越好。

| 规模 | 推荐选型 | 理由 |
|------|---------|------|
| 小规模（几千条） | ChromaDB | 轻量、本地可用、Python 原生 |
| 中规模（几万条） | Qdrant / ChromaDB | 性能开始需要考虑扩展性 |
| 大规模（10万+） | Qdrant / Milvus | 需要分布式、向量索引优化 |
| 商业化/不想运维 | Pinecone | 完全托管，但有成本 |

**关键原则：** 不要把具体数据库写死在代码里，用抽象层隔离。

## 附录 C：任务分级原则（D0-D3）

> 来源：Sliver Vibe Coding。任务规模决定治理深度，小任务不大干，大任务不漏控。

| 级别     | 说明                                | 治理要求                 |
| ------ | --------------------------------- | -------------------- |
| **D0** | 单点小改动（如改个按钮间距、修复一个明显 bug）         | 窄查、窄改、窄验，不走完整流程      |
| **D1** | 单 owner 普通任务（如加一个新接口、写一个函数）       | 标准流程，代码 + 基础验证       |
| **D2** | 多 owner 变更（如改数据库结构 + 改 API + 改前端） | 先设计、再实施、需要明确验收条件     |
| **D3** | 基础决策（如换框架、换数据库、重构架构）              | 重大决策，需要完整评估 + 用户确认影响 |

**原则：** 不要因为术语复杂就把小任务放大，也不要因为任务小就跳过必要的验证。

## 附录 D：防假完成规则

> 来源：Sliver Vibe Coding。AI 说"完成了"不代表真的完成了。

**核心铁律：没有新鲜验证 = 没完成。**

| 验证类型 | 有效                    | 无效（假验证）          |
| ---- | --------------------- | ---------------- |
| 代码审查 | 看懂了逻辑，知道对在哪           | 看都没看就说"写得不错"     |
| 测试   | 测试真的跑了，结果是通过的         | 测试写了但没跑，或者跑了没看结果 |
| 运行验证 | 本地跑过 / API 测过 / 浏览器看过 | 代码写了就当完成了        |
| 用户验收 | 用户亲自用过，说"可以"          | AI 说"用户应该会满意"    |

**三次修复失败规则：** 如果同一个问题 AI 改了三次还是不对，停下来。回到架构层面诊断，不要继续局部打补丁。

## 附录 E：单一 owner 原则

> 来源：Sliver Vibe Coding。每个概念只归一个地方管，不散落在多个文件里。

**问题症状：**
- 一个概念同时出现在 README、代码注释、prompt 文档里，说法不一致
- 改了一处，另一处忘了改
- 不知道哪个是最新的

**解决：**
- 每个重要决策（架构/选型/接口约定）只写在一个地方
- 其他地方引用它，不要复制它
- 每次改动只改 owner 文件，其他引用自动失效（会暴露问题）
