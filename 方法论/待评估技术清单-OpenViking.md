## 一、技术概述

**定位**：专为 AI Agent 设计的上下文数据库（Context Database）。

**核心理念**：用**文件系统范式**替代传统扁平 RAG，将 Agent 的所有上下文（记忆/资源/技能）统一组织在虚拟文件系统中。

```
viking://
├── memory/
│   ├── session/   # 会话记忆
│   ├── task/      # 任务记忆
│   └── long_term/ # 长期记忆
├── resources/
│   ├── docs/      # 文档资源
│   ├── code/      # 代码资源
│   └── knowledge/ # 知识库
└── skills/
    ├── tools/     # 工具能力
    └── workflows/ # 工作流
```

**出品方**：字节跳动火山引擎 Viking 团队（VikingDB 向量数据库起家，2019年内部大规模验证）。

## 二、核心技术机制

### 2.1 三层加载策略（L0/L1/L2）

每个文件自动生成三层，按需加载：

| 层级 | 名称 | 内容 | Token 量 | 加载时机 |
|---|---|---|---|---|
| L0 | 摘要层 | 一句话概括 | ~100 tokens | 始终加载（快速过滤） |
| L1 | 概述层 | 核心信息+使用场景 | ~2K tokens | 按需加载（规划决策） |
| L2 | 详情层 | 完整原文 | 100% | 精确查询时加载 |

**实测效果**：降低 80-91% token 消耗。

### 2.2 目录递归检索

模拟人类查资料思路：
1. 先通过语义理解找到正确的"文件夹"
2. 在目录内部做精确语义匹配
3. 递归追踪子目录和引用文件
4. 完整保留检索轨迹，可视化可调试

**效果**：复杂意图查询召回精度提升约 40%。

### 2.3 可观测检索轨迹

每次检索的目录浏览、文件定位轨迹全部记录：
- 从哪个目录开始
- 经过哪些节点
- 最终从哪些文件加载了内容
- 各文件权重分配

→ 开发者可直接看到"Agent在想什么"，定位召回错误。

### 2.4 自动 Session 管理（自进化）

会话结束后自动触发记忆提取：
- **用户记忆更新**：用户偏好相关记忆 → Agent 回应更贴合需求
- **Agent 经验积累**：操作技巧/工具使用经验 → 后续任务高效决策

→ Agent 越用越聪明，执行 10 次同类任务后，第 11 次上下文质量明显优于第 1 次。

### 2.5 8类记忆结构化提取

| 用户侧 | Agent侧 |
|---|---|
| profile（用户画像） | cases（案例经验） |
| preferences（偏好） | patterns（模式） |
| entities（实体） | tools（工具使用） |
| events（事件） | skills（技能） |

LLM 去重决策：CREATE / MERGE / SKIP / DELETE 四分类。

## 三、与主流方案对比

| 维度 | 传统 RAG | LangChain Memory | **OpenViking** |
|---|---|---|---|
| 存储组织 | 扁平向量库 | 多种 Memory 类型 | **文件系统层级（L0/L1/L2）** |
| Token 控制 | 手动截断 | 部分自动 | **L0/L1/L2 自动分层（↓80-91%）** |
| 检索精度 | 语义相似度 | 类型匹配 | **目录递归+语义（↑40%）** |
| 调试能力 | 几乎没有 | 有限 | **完整可视化检索轨迹** |
| 记忆进化 | 不支持 | 不支持 | **自动经验提炼+自进化** |
| 覆盖范围 | 仅资源 | 仅记忆 | **记忆+资源+技能统一** |
| 部署复杂度 | 低 | 中 | **中（pip install / Docker，Python+Rust 核心）** |

## 四、与 QClaw 记忆系统的本质对比

### QClaw 记忆系统（当前）

```
三层协作系统：
├── L1 启动文件（MEMORY.md / SOUL.md / USER.md）
│   → 每次会话自动加载
│   → 手动维护（人工决定写什么）
│   → 无自动分层（整篇加载）
├── L2 每日日志（memory/YYYY-MM-DD.md）
│   → 按需读取，不每次加载
│   → 原始流水账
└── L3 对话压缩（lossless-claw 自动）
    → 自动压缩对话历史
    → 可用 lcm_grep 检索
    → 不自动提取精华，需人工判断
```

### OpenViking（目标形态）

```
三层协作系统：
├── L0 摘要层（~100 tokens）
│   → 始终加载
│   → 自动生成（LLM 提炼）
│   → 无人工维护成本
├── L1 概述层（~2K tokens）
│   → 按需加载
│   → 自动生成结构化概览
└── L2 详情层（完整原文）
    → 精确查询时加载
    → 自动压缩+经验提炼
```

### 核心差距

| 维度 | QClaw 当前 | OpenViking 目标 |
|---|---|---|
| **记忆写入** | 人工判断写什么 | LLM 自动提炼 |
| **分层加载** | 无（全量加载） | L0/L1/L2 自动按需 |
| **记忆进化** | 无（人工整理周总） | 自动会话后提炼 |
| **检索调试** | 无 | 可视化检索轨迹 |
| **部署复杂度** | 零（纯文件） | 中（pip/Docker，Python+Rust 核心） |
| **适用范围** | 单 Agent | 多 Agent 共享 |

### 启发：哪些可以借鉴

| 启发点 | 能否现在用 | 怎么用 |
|---|---|---|
| **L0/L1/L2 分层思想** | ✅ 可以 | MEMORY.md 里建立类似分层：核心结论（L0）/ 详细规则（L1）/ 原始日志（L2） |
| **自动记忆提炼** | ❌ 暂不需要 | QClaw 有人工维护，且当前会话量未达到需要自动化的规模 |
| **可视化检索轨迹** | ❌ 暂不需要 | 我们是人工检索，没有 RAG 黑盒问题 |
| **多 Agent 共享记忆** | ⚠️ W17 后 | 小舟/Codex 进场后可能需要，但到时候直接集成 OpenViking 更高效 |

## 五、决策记录

### 结论：现在不需要，W17 后评估。

### 原因（论证式）

**利好（未来评估）**：
- 若 W17 后做多 Agent 协作系统，OpenViking 的"跨 Agent 统一记忆层"有价值（已集成 Codex/Claude Code/LangChain，生态成熟度高）
- "目录递归检索"思想可用于知识库导航增强（MOC 进化版）
- L0/L1/L2 分层思想可迁移到 MEMORY.md 的整理方式

**代价（现在集成）**：
- 推翻 W10-W11 的 bge+Chroma 技术栈，W12 项目期从零踩坑
- AGPL-3.0 许可证对商业使用有限制
- 早期版本（v0.4.x），API 仍不稳定（2.4 天一版本）
- 黑盒记忆 vs 现有白盒可审计，失去"人类拍板"控制权

**判断**：QClaw 现有记忆系统是"人类可审计、白盒可控"的架构，与 OpenViking"Agent 自管理、黑盒"的路线相反，不是升级关系，是不同路线。W17 评估分量因生态集成成熟而应加重，但"现在不用"结论不变。
