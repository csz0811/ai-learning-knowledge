# 隐性需求发现方法（living doc）

> 创建：2026-08-24（W12-D2）｜触发：用户反思「隐性功能无法从外部框架学到，靠构建中意外得知」
> 性质：**living doc**，不全靠一次写全——靠小舟检查 + 每项目意外发现持续扩充
> 关联：[[用户工作方法与合作偏好观察]] [[AI认知与使用方法]] [[QClaw记忆系统完整说明]]

## 一、核心结论
- 隐性需求生于**真实场景**，不生于教程/框架。教程教「X 怎么做」，教不出「你的 X 在此业务还需什么」。
- **无法事前全避免**，但能把「意外发现」转成「开工前系统检查」。
- 本卡 = 用户自己的隐性知识沉淀库（外部框架没有，只有踩过/聊过才长得出）。

## 二、四个机制（把意外变系统）
1. **每次意外发现 → 抽成模式卡/追加本卡**：不只用一次。未来项目开头先翻本卡。
2. **常设检查清单（见第三节）**：项目开头过一遍类别，大部分隐性需求跑不掉。
3. **「事后会后悔没建什么」pre-mortem**：开工中/前问「三个月后回头看会骂自己没建什么」。
4. **真实项目早做 + 当采矿**：教程给「怎么做」，真实项目给「需要什么」，不可互替。

## 三、隐性需求检查清单（种子版 · 待小舟/W17 后扩充）
> ⚠️ 本清单是**起点不是终点**。用户自认「很多考虑不到」——故设计为由小舟检查 + 每项目追加来长全，不全靠一次性列全。
> 用法：项目开头逐类过；小舟 review 时对照补充；每次意外发现追加一类/一条。

### A. 数据采集 / 反馈闭环
- [ ] 上线后最缺什么数据？（→ bot 答不出的问题落日志，反哺 KB：见项目主框架点1）
- [ ] 系统有没有「自我滋养」回路？（使用数据 → 改进）

### B. 边界 / 容错
- [ ] 什么输入会答错 / 崩溃 / 超时？
- [ ] 检索不到 / 低置信时怎么兜底？（「不知道」软约束够不够）
- [ ] 并发 / 异常 / 空值怎么处理？

### C. 成本护栏
- [ ] 每次调用花多少 token / 钱？有无上限？
- [ ] 大文档 / 高频请求会不会爆？

### D. 可维护性 / 交接
- [ ] 谁维护？配置是否外置（不写死）？
- [ ] 知识/内容更新要不要碰代码？（→ 独立数据文件，如 faq_seed.md）
- [ ] 新人/外部工具接手能否读懂？（→ 业务背景包 + 结构说明）

### E. 合规 / 风险
- [ ] 对外文本要不要过违禁词/合规？（→ douyin-sensitive-check）
- [ ] 数据隐私 / 授权 / 平台规则红线在哪？

### F. 可观测 / 复盘
- [ ] 哪些判断以后要复盘？（→ 日志 / 溯源 metadata）
- [ ] 出事能不能定位来源？（→ retriever metadata 溯源）

### G. 体验 / 交付
- [ ] 前端/界面是不是交付必需品？（创业者视角，非代码）
- [ ] 客户愿付费的标准是什么？

> 🔲 待小舟（W17 项目搭子）补充：小舟从项目经验追加其领域盲区条目
> 🔲 每项目意外发现：追加一类/一条，并标注来源日期

## 四、协作机制（小舟检查 → 用户抽模式 → 回填，防思路依赖）
- 用户无项目经验 → 检查清单天然有盲区 → **小舟（项目搭子/质检）做检查，用户根据小舟提出的举一反三**。
- ⚠️ 防陷阱：不能只靠小舟代想（= 思路依赖复发）。正确闭环：
  1. 小舟 review 项目，标出隐性需求缺口
  2. 用户不只改项目，而是**抽出「这类需求的模式」**追加进本卡第三节
  3. 下次用户自己能用模式 catch 同类，小舟负担递减
- 本卡 therefore 是用户**内化外部大脑**的载体：小舟 外脑 → 模式卡 → 用户内脑。

## 五、living doc 声明
本卡不全靠一次写全。全面性来自**迭代 + 小舟**，非一次性穷举（穷举既 noise 又仍不全）。每项目结束复盘时追加，小舟进场后由其扩充。
