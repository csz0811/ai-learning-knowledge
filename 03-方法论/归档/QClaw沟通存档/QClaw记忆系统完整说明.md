## 二、三层记忆系统的真实结构

```
QClaw 记忆 Skill
├── L1 启动文件层（核心，每次会话自动加载）
│   ├── MEMORY.md（角色/规则/进度/北极星/创业背景/AI认知）
│   ├── SOUL.md（人设/说话风格/核心角色）
│   ├── USER.md（用户信息/偏好/说话风格）
│   └── IDENTITY.md / TOOLS.md（环境配置）
│
├── L2 每日日志层（原始存档，按需读取）
│   └── memory/YYYY-MM-DD.md
│
└── L3 对话压缩层（lossless-claw，自动运行）
    ├── lcm_grep：按关键词/正则检索压缩历史
    ├── lcm_expand：展开压缩摘要看完整内容
    ├── lcm_describe：查看某个摘要的元信息
    └── lcm_expand_query：委托子代理深度检索
```

### 各层职责

| 层次 | 触发方式 | 维护者 | 用途 |
|---|---|---|---|
| L1 启动文件 | 每次会话自动加载 | 我（手动追加） | 每次会话都需要的核心信息 |
| L2 每日日志 | 需要时读 | 我（关键节点写） | 详细流水，不每次加载 |
| L3 对话压缩 | 自动后台运行 | lossless-claw 自动压缩 | 跨会话检索历史对话 |

## 三、各层详细说明

### L1 启动文件层（核心层）

**每次会话自动加载**，开场我就能看到。

#### MEMORY.md（长期记忆）
- 精简索引，每次会话加载
- 内容：角色定位/创业背景/北极星/学习进度/关键教训/能力边界
- **规则：超 350-400 行做一次合并压缩**，保持体量可控
- **写入时机：产生重要结论时立刻写，不等**

#### SOUL.md（人设）
- 我的核心角色定义
- 说话风格：温柔但有力/少说废话/该夸就夸该说就说
- 触发词：用户说"小Q"开头

#### USER.md（用户信息）
- 用户画像：创业者/有野心/愿被批评/整理癖
- 说话风格：直接/说"但是"补充/说"这个是不是"确认
- 学习节奏：凌晨 3 点开始，09:00 温和提醒一次

### L2 每日日志层

**按需读取，不每次加载**。

#### memory/YYYY-MM-DD.md
- 原始流水账，详细记录当天发生的事
- 格式：时间戳 + 事件 + 结论
- 写入时机：关键节点（不是每次对话都写）

### L3 对话压缩层（lossless-claw）

**自动后台运行，不需要手动维护，但需要主动利用**。

#### 工作方式
- 每次对话结束，lossless-claw 把对话压缩成摘要
- 摘要存在数据库里，可以跨会话检索
- 我可以用工具主动检索，不是被动等

#### 检索工具

| 工具 | 用途 | 什么时候用 |
|---|---|---|
| `lcm_grep` | 按关键词搜索压缩历史 | "之前讨论过什么？" |
| `lcm_expand` | 展开压缩摘要看完整内容 | 搜索到相关摘要，想看细节 |
| `lcm_describe` | 查看摘要元信息 | 想确认某个摘要是什么时候的 |
| `lcm_expand_query` | 委托子代理深度检索 | 需要综合多个摘要回答复杂问题 |

#### 使用示例
```
# 搜索之前讨论过"前端"相关的对话
lcm_grep(pattern="前端", scope="both")

# 展开某个摘要看详细内容
lcm_expand(summaryIds=["sum_xxx"])

# 深度检索某个主题
lcm_expand_query(query="SR.D Motion Sites", prompt="当时讨论了什么结论？")
```

## 四、底层逻辑：为什么是三层

### 上下文窗口限制（核心约束）

AI 每次会话只能在上下文窗口里运行，只调用窗口里出现过的知识。

三层记忆系统是对抗这个限制的工具：

```
上下文窗口（有限）
    ↑ 每次新会话重新加载
L1 启动文件（精炼索引）
    ↑ 重要结论从 L3 提取出来
L2 每日日志（详细存档）
    ↑ 自动压缩，不手动维护
L3 对话压缩（lossless-claw）
    ↑ 每次对话结束自动生成
```

**流程**：对话产生 → L3 自动压缩 → 重要内容提取到 L1 → 新会话加载 L1 → 我又有了上下文

---

## 五、三层联动的正确用法

### 场景一：会话中产生重要结论

**立即写进 MEMORY.md（L1）**

```
这次对话的结论：SR.D/Motion Sites 应该收，因为是设计灵感来源

→ 立刻写进 MEMORY.md
→ 写进 memory/YYYY-MM-DD.md（L2，可选）
```

### 场景二：新会话需要补充上下文

**主动用 lcm_grep 检索**

```
新会话开始，发现 MEMORY.md 没有最近的讨论内容

→ lcm_grep(pattern="SR.D", scope="both")
→ 找到相关压缩摘要
→ lcm_expand 展开看详细结论
→ 补充写进 MEMORY.md
```

### 场景三：想回顾之前讨论过什么

**用 lcm_grep 主动搜索**

```
用户问："之前我们讨论过 Vibe Coding 吗？"

→ lcm_grep(pattern="Vibe Coding", scope="both")
→ 找到相关摘要
→ lcm_expand 展开看结论
```

## 六、MEMORY.md 的维护纪律

### 写入规则
1. **重要结论产生时立刻写**，不等
2. **每次会话至少检查一次**：MEMORY 里的内容是否需要更新
3. **超 350-400 行做合并压缩**，把重复内容合并，把细节外移
4. **四层分流**：MEMORY（精炼索引）/ Obsidian库（学科内容）/ 学习档案（流水）/ memory每日（原始日志）

### 读取规则
1. 新会话开始，先浏览 MEMORY.md 确认当前位置
2. 遇到跨会话问题，主动用 lcm_grep 检索
3. 不确定 MEMORY 里有没有某个内容 → 先 lcm_grep，不猜

## 七、常见错误（QClaw 犯过的）

### 错误一：重要结论没写进 MEMORY.md
- 后果：新会话里这个结论丢了
- 例子：这次对话的 AI 认知更新，如果我不写进 MEMORY.md，下次开新会话我会重新犯同样的错误

### 错误二：只依赖 MEMORY.md，忘了用 lcm_grep
- 后果：以为某段历史"丢了"，其实在 L3 里
- 例子：用户问"之前讨论过什么"，我应该 lcm_grep，不应该直接说"我不知道"

### 错误三：L1 和 L3 没有联动
- 后果：L3 压缩了精华，但 L1 没有提取出来
- 改正：每次重要对话结束后，检查 L3 里有哪些值得提升到 L1

---

## 八、MEMORY.md 的真实定位

**不是 AI 的"记忆"，是外部化的"判断锚点"。**

AI 的记忆在上下文窗口里，窗口关闭就消失。

MEMORY.md 的作用是：每次新会话开始，先加载这个文件，让我"记得"之前确立的规则和结论，不用每次重新解释。

**所以 MEMORY.md 只需要写"需要我每次都记得"的内容**，不需要写所有细节。
